# 人工無障礙測試 runbook（螢幕閱讀器與高對比）

**建立日期：** 2026-07-24

**適用範圍：** `apps/web` 的患者預約頁與工作臺，跑在打包後的 `apps/web/dist`。

## 1. 為什麼還需要人工測試

自動化已經在 CI 擋掉一部分問題：`tests/e2e/accessibility.spec.ts` 用 axe 掃描三個
畫面，serious／critical 違規會讓 CI 失敗（2026-07-24 靠它抓到並修正了三個真實
的對比與鍵盤問題）。

但 axe 這類工具能自動判定的，只有「機器可判定」的那一部分 WCAG 準則——對比、
缺少的名稱、地標結構、表單標籤。它**無法**判定：

- 播報出來的句子是否讓人聽得懂、順序是否合理；
- 焦點在彈窗開關、分頁切換、非同步更新後是否落在正確的位置；
- 動態更新是否真的被播報（`aria-live` 存在 ≠ 被播報）；
- Windows 高對比模式把作者色彩抹掉後，狀態是否還看得出來。

這四類只能由人操作。**「axe 全綠」不得作為本 runbook 的替代品。**

## 2. 什麼時候要跑

| 時機 | 範圍 |
| --- | --- |
| 改到表單、彈窗、分頁、焦點管理或狀態播報 | 受影響的那一節 |
| 改到 `styles.css`／`workbench.css` 的顏色或焦點樣式 | 第 6 節（高對比） |
| 每次 checkpoint 複查 | 全部 |
| 上線證據包（D-011） | 全部，且需附紀錄 |

## 3. 環境準備

1. 建置並啟動打包產物（人工測試必須跑在真正會部署的 dist 上）：

   ```bash
   corepack pnpm build
   ```

   ```bash
   TEST_ONLY_WEB_ENABLED=true WEB_ROOT=dist TEST_ONLY_WEB_PORT=3210 corepack pnpm serve:dist
   ```

   PowerShell 沒有「環境變數前綴」語法，要先 `$env:TEST_ONLY_WEB_ENABLED='true'`
   等三個變數再執行 `corepack pnpm serve:dist`。

2. 螢幕閱讀器（擇一即可，兩個都跑更好）：
   - **Windows：NVDA**（免費）。啟動後按 `NVDA+空白` 確認在瀏覽模式。
   - **macOS：VoiceOver**（`Cmd+F5`）。
3. 瀏覽器：Chrome 或 Edge 最新版。NVDA 搭 Chrome、VoiceOver 搭 Safari 是最貼近
   實際使用者的組合。
4. 高對比：Windows「設定 → 協助工具 → 對比佈景主題」選一個（建議「水漾」與
   「沙漠」各測一次）。沒有 Windows 時，用 Chrome DevTools →「Rendering」→
   `Emulate CSS media feature forced-colors: active`；這是模擬，**不能**當成
   最終證據，只能用來先抓明顯問題。

## 4. 測試 A：螢幕閱讀器走完患者預約（`/booking`）

全程只用鍵盤，不碰滑鼠。

| # | 操作 | 通過條件 |
| --- | --- | --- |
| A1 | 載入頁面，用 `H` 逐一跳過標題 | 標題層級是連續的（h1 → h2 → h3），沒有跳級；第一個 h1 說得出這是哪一間診所的預約頁 |
| A2 | `D` 或 `Ctrl+Alt+方向鍵` 巡覽地標 | 有 banner／main／contentinfo；主要內容不在任何多餘的巢狀地標裡 |
| A3 | Tab 到四步驟指示器 | 目前步驟被播報為「目前的步驟」（`aria-current="step"`），不是只靠顏色 |
| A4 | 依序填寫姓名、電話、生日三格；分別驗證身分證／居留證與「外籍人士」護照路徑，再走健保卡、門診／來源標籤、條件式介紹人、患者備註及告知草稿已讀勾選 | 每個欄位與群組都念得出標籤、選填狀態及格式要求；切換外籍人士時只留下正確的證件欄；欄位錯誤會被念出並與欄位關聯 |
| A5 | 選擇時段（日期分組清單） | 念得出「日期＋時間＋初診／回診」；已過去或不可預約的時段不會被當成可選項目 |
| A6 | 送出預約 | `#patient-status`（`role="status"`、`aria-live="polite"`）的成功或失敗訊息會被自動播報；失敗時念得出**原因**，不是只有「失敗」 |
| A7 | 送出後檢視我的預約 | 新預約出現在清單且被念得出；身分證、居留證或護照顯示為遮罩，**不得**念出完整號碼 |

## 5. 測試 B：螢幕閱讀器走完工作臺（`/`）

| # | 操作 | 通過條件 |
| --- | --- | --- |
| B1 | 首屏登入閘門 | 帳號與密碼欄位有標籤；「這不是安全邊界」的說明念得到 |
| B2 | 以 `admin` / `beauessence-admin` 登入 | 登入後焦點移入主要內容，不是留在已消失的表單上 |
| B3 | 用 Tab 或方向鍵切換工作臺分頁 | 目前分頁被播報為目前位置（`aria-current`）；切換後焦點落在新分頁的內容起點 |
| B4 | 跳過導覽連結（skip link） | 第一個 Tab 就是「跳到主要內容」，按下後焦點真的移到 `#main-content` |
| B5 | 建立一筆預約 | 成功訊息由頂端 `#status`（唯一的 `aria-live` 播報點）播報，同一句話也出現在按鈕旁邊 |
| B6 | 對預約執行「到診」 | 自製確認彈窗開啟時焦點進入彈窗、`Esc` 可關閉、關閉後焦點回到原本的按鈕 |
| B7 | 逐筆回診確認 | 日期與時間欄位念得出限制（僅營業日的回診網格）；被拒絕時念得出原因 |
| B8 | 主管刪除預約 | 必填理由欄位念得出來；刪除後清單更新有被播報 |
| B9 | Tab 到週檢視 `#week-view` | 可以取得焦點（`role="group"`、`tabindex="0"`），並能用方向鍵捲動 |
| B10 | 任一非同步操作進行中 | 按鈕在 pending 期間換成清楚的忙碌文字且不可重複觸發；按鈕本身不設 `aria-busy`，由狀態列公告；失敗後「重試」按鈕念得到 |
| B11 | 櫃台登入後嘗試主管分頁與受限 hash | 主管導覽與內容不在 DOM；受限 hash 回到首頁並念出權限提示 |
| B12 | 開啟通知 popover 後按 `Esc` | 清單關閉、焦點回到通知鈴鐺，且 header 不位移 |
| B13 | 患者頁在維護模式啟用時開啟 | 焦點進入維護標題；預約流程不在互動與無障礙樹；恢復後流程才重新出現 |

## 6. 測試 C：Windows 高對比／forced-colors

開啟對比佈景主題後，患者頁與工作臺各走一次。

| # | 檢查 | 通過條件 |
| --- | --- | --- |
| C1 | 焦點框 | 每個可聚焦元素都看得到焦點框，且用的是系統色（`styles.css` 的 `@media (forced-colors: active)`） |
| C2 | 目前分頁 | 底色被系統抹掉後，仍以 `Highlight` 外框標示（`workbench.css` 的 forced-colors 區塊） |
| C3 | 主要／次要按鈕 | 兩者仍可分辨，且都看得到邊界 |
| C4 | 狀態色（成功／警告／錯誤） | 不只靠顏色——文字或圖示仍說得出狀態 |
| C5 | 404 頁 | `error.css` 的 forced-colors 區塊生效，連結與標題都可辨識 |
| C6 | 四種主題（自動／淺色／護眼／深色） | 開啟高對比後，四種主題都不會出現看不見的文字 |

## 7. 測試 D：只用鍵盤與縮放

| # | 檢查 | 通過條件 |
| --- | --- | --- |
| D1 | 全站只用鍵盤 | 沒有任何只能用滑鼠完成的操作；沒有鍵盤陷阱 |
| D2 | 瀏覽器縮放 200% | 內容不重疊、不被裁切、不需要水平捲動（WCAG 1.4.4） |
| D3 | 視窗寬 320px | 內容以單欄重排，不出現水平捲軸（WCAG 1.4.10） |
| D4 | `prefers-reduced-motion: reduce` | 動畫被關閉（`styles.css` 已有對應區塊） |

## 8. 判定與紀錄

- **通過**：上表每一列都符合通過條件。
- **失敗**：任何一列不符合。修正後**重跑整節**，不是只重跑那一列——焦點與播報
  的問題常常互相牽動。

## 8-b. 待實機讀屏確認的項目

自動化擋得住結構性錯誤，但擋不住「唸起來對不對」。以下項目需要真的用螢幕閱讀器
聽過才能定案：

1. **資料表在手機寬度下的欄位名是否重複朗讀。** 手機版把表格改成堆疊
   （`display: block`），欄位名由 `td::before` 的 `content: attr(data-label)`
   帶出來。表格語意已用 ARIA role 釘回去，表頭關聯仍成立，因此讀屏**可能**唸成
   「時間 時間 08:30」。若確認重複且干擾，改法是每格加一個 `aria-hidden="true"`
   的 `<span>` 取代 `::before`——代價是每列多幾個節點。
   **2026-07-25 起這件事影響六張表**（櫃台處理清單、排班 ×3、個案管理、月度統計、
   員工權限、稽核紀錄），不再只有櫃台清單，所以實機驗證的價值比先前高。
2. **待處理狀態的公告時機。** 按鈕在忙碌期間**不設** `aria-busy`（那是 live
   region 的屬性，會把元素自己的名稱藏起來），改由 `role="status"` 的狀態列
   公告。要確認的是：動作很快結束時，狀態列的訊息是否還來得及被唸出來。
3. **批次選取的每列名稱是否唸得出「在勾誰」。** 每個選取方塊的 `aria-label` 是
   「選取 ⟨患者⟩ ⟨日期時間⟩」。要確認的是：只在表單控制項之間跳（不逐格讀表格）
   時，這個名稱夠不夠分辨；以及全選方塊在部分選取時是否唸成 mixed／partially
   checked。全選刻意放在表格**外面**——放進選取欄的表頭會讓它變成每一列方塊的
   欄位名。
4. **欄位排序的狀態變化是否被公告。** 排序用 `aria-sort`（只掛在當前排序的那一欄
   的 `th` 上）。要確認的是：按下欄名按鈕後，讀屏是否讀得到新的排序方向——焦點會
   被放回同一顆按鈕，理論上重新聚焦時會帶出 `aria-sort`。若實測沒有播報，補一句
   到 `role="status"` 的狀態列即可，不要改成 live region。
5. **清單摘要的公告是否堪用。** 全站清單容器都不是 live region，改由簡短的
   `.result-summary`（「N 筆結果」）公告。要確認的是：篩選或搜尋後，這一句是否
   確實被唸出來，且不會蓋掉使用者正在讀的內容。

## 9. 已知限制

- 目前的驗證對象是**合成資料**的測試環境。真實患者資料進場後（D-001～D-003
  核准），本 runbook 必須重跑，並額外檢查遮罩與錯誤訊息不會洩漏個資。
- 行動裝置的螢幕閱讀器（TalkBack／iOS VoiceOver）尚未納入。手機版是患者端的
  主要入口，上線前應補一次；這需要實機，不能靠模擬器。
- 本 runbook 不涵蓋文件（PDF／匯出檔）的無障礙。目前唯一的匯出是 `.ics`
  行事曆檔，由使用者自己的行事曆程式呈現，不在本平台的責任範圍。
