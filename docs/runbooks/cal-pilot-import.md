# 日曆搬運工具 使用教學

## 這個工具在做什麼

把診所真實日曆上的預約，**只保留「幾點」和「一個代號」**，複製到另一本測試日曆。

```text
真實日曆                          測試日曆
─────────                        ─────────
王小明 14:00 鼻中膈手術    ──▶    患者 A17  14:00
電話 0912-345-678
台北市…                          （姓名、電話、病症、地點全部丟掉）
```

為什麼要這樣做：工作臺的週曆需要「看起來像真的一週」才測得出問題，但**沒有必要
知道那是誰、來看什麼**。所以只搬時間和代號。

## 三個保證

1. **不會改到真實日曆。** 讀取的程式碼裡**根本沒有寫入功能**——不是「有但不用」，
   是打字都打不出來。有測試證明這件事。
2. **姓名、電話、病症不會被搬過去。** 有測試拿假的「王測試／0912345678／
   A123456789／鼻中膈」去跑，確認輸出裡一個字都沒有。
3. **重跑不會變兩筆。** 同一筆搬第二次會被當成「已經有了」，不會重複。

## 開始之前，你要先有三樣東西

| 要準備的 | 怎麼弄 | 注意 |
| --- | --- | --- |
| **一本空的測試日曆** | Google 日曆左邊「其他日曆」→ ＋ → 建立新日曆 | 取名時**不要**寫診所名字 |
| **兩個機器人帳號的金鑰檔** | Google Cloud 主控台建立服務帳號後下載 JSON | **必須是兩個不同的**，程式會檢查 |
| **一組自訂密碼** | 你自己想一串，至少 16 個字 | 代號是由它算出來的；換掉它代號就全變 |

> **唯讀那組要設定成唯讀。** 在真實日曆的「共用設定」裡，把它加為
> 「**僅能查看所有活動詳細資訊**」，**不要**給編輯權限。這是最重要的一道防線。

## 建議：先用兩本全新日曆演練一次

**不要一開始就對真實日曆跑。** 先開**兩本全新的空日曆**：

| 日曆 | 角色 | 放什麼 |
| --- | --- | --- |
| **假來源** | 扮演「真實日曆」 | 匯入下面產生的合成事件 |
| **測試目的地** | 真正的目的地 | 空的 |

這樣整條管線照跑、Google API 照打、權限照設，但**完全沒有任何真實病患資料**。
跑通了之後要換成真實日曆，只是改一個環境變數而已。

### 產生假來源資料

```powershell
node apps/worker/dist/pilot/make-source-fixture.js > 假來源.ics
```

會產生約 29 筆合成事件，時間照診所實際營業時間（週三～五 12:00–20:00、
週六 10:00–18:00），姓名都是「測試一」「測試二」這種明顯不是真人的字樣。

裡面**刻意混入了五種邊界情況**，因為平順的資料測不出問題：

| 放進去的 | 預期結果 |
| --- | --- |
| 整天事件（休診公告） | 被擋下，計為 `all_day_unsupported` |
| 跨日事件（設備維護） | 被擋下，計為 `multi_day_unsupported` |
| 同時段兩筆 | 都通過（初診／回診是兩條人力線） |
| 長診（跨時段） | 通過 |
| 營業時間外的內部會議 | 通過消毒，但工作臺可能不顯示——**那本身是個發現** |

### 匯入假來源日曆

Google 日曆 → 右上齒輪 →「設定」→ 左邊「匯入及匯出」→ 選剛才的 `.ics` 檔 →
「新增至日曆」選**假來源**那本 → 匯入。

### 預期結果

拿這份 fixture 實際跑過消毒器，結果是：

```text
29 筆 → 通過 27 筆、擋下 2 筆
擋下原因：all_day_unsupported 1、multi_day_unsupported 1
```

輸出長這樣（只有三個欄位，姓名完全不見）：

```text
{"pilotId":"f2b96e2d...","displayLabel":"患者 C70","startsAt":"2026-08-26T04:00:00.000Z"}
```

**你跑出來的數字應該一樣。** 不一樣的話就是哪裡設定不對。

## 建兩個機器人帳號（只要做一次）

程式不能用你的帳號登入——那要按同意畫面，但沒有人坐在旁邊按。所以要建**服務帳號**，
可以想成「機器人員工」：它有自己的 email，你把日曆分享給它，它就進得去。

**為什麼要兩個而不是一個**：如果同一個機器人既能讀真實日曆、又能寫測試日曆，那
「讀寫分離」就只是嘴上說說。分成兩個，讀的那個在 Google 的權限層級就寫不了東西。

| 機器人 | 能碰什麼 | 給什麼權限 |
| --- | --- | --- |
| **A 號** | 真實日曆 | **只能查看**（唯讀） |
| **B 號** | 測試日曆 | 可以修改 |

A 號**完全碰不到**測試日曆，B 號**完全碰不到**真實日曆。

### 步驟

1. 開 <https://console.cloud.google.com/>，用診所的 Google 帳號登入。
2. 左上角專案選單 →「新增專案」→ 取個名字（例如 `clinic-cal-pilot`）→ 建立。
3. 搜尋列打 `Google Calendar API` → 進去 → 按「**啟用**」。
   忘記這步的話，之後會一直出現權限錯誤。
4. 左邊選單「IAM 與管理」→「**服務帳戶**」→「建立服務帳戶」。
   - 名稱打 `cal-pilot-reader` → 建立 → 後面兩個「選用」步驟直接跳過 → 完成。
   - **再做一次**，名稱打 `cal-pilot-writer`。
5. 現在清單上有兩個。**分別**點進去 →「金鑰」分頁 →「新增金鑰」→「建立新金鑰」→
   選 **JSON** → 下載。
   - 你會拿到兩個 `.json` 檔。建議改名成 `a-讀取.json`、`b-寫入.json`，放在
     一個你記得住的資料夾。
   - **這兩個檔案等於鑰匙。不要用 email 或通訊軟體傳，也不要放進任何專案資料夾。**
6. 順手把兩個機器人的 email 記下來（在服務帳戶清單裡，長得像
   `cal-pilot-reader@專案名.iam.gserviceaccount.com`）。下一步要用。

### 把日曆分享給機器人

**真實日曆 → 分享給 A 號（唯讀）**

1. Google 日曆 → 左邊找到診所那本 → 滑鼠移上去 → 三個點 →「設定和共用」。
2. 往下找「與特定使用者或群組共用」→「新增使用者」。
3. 貼 **A 號的 email**。
4. 權限下拉選單選「**僅能查看所有活動詳細資訊**」。
   **絕對不要選「變更活動」或「進行變更並管理共用設定」。**
5. 傳送。

**測試日曆 → 分享給 B 號（可修改）**

1. 同樣路徑，但這次是你新建的那本測試日曆。
2. 貼 **B 號的 email**，權限選「**變更活動**」。
3. 傳送。

### 拿到兩本日曆的 ID

在每本日曆的「設定和共用」頁面往下捲，找「**日曆 ID**」，長得像
`abc123@group.calendar.google.com`。兩本都複製下來。

> **這兩個 ID 和兩個金鑰檔都只留在你自己的電腦上。** 它們填進下面的 PowerShell
> 設定，程式從那裡讀。不需要給任何人。

## 設定（PowerShell）

打開 PowerShell，一行一行貼上去，把 `<...>` 換成你自己的值：

```powershell
$env:CAL_PILOT_SOURCE_CALENDAR_ID = '<真實日曆的 ID>'
$env:CAL_PILOT_TEST_CALENDAR_ID   = '<測試日曆的 ID>'
$env:CAL_PILOT_SOURCE_KEY_FILE    = '<A 號機器人的金鑰檔路徑>'
$env:CAL_PILOT_WRITER_KEY_FILE    = '<B 號機器人的金鑰檔路徑>'
$env:CAL_PILOT_PSEUDONYM_KEY      = '<你自己想的一串密碼>'
$env:CAL_PILOT_WINDOW_DAYS        = '14'
$env:CAL_PILOT_MAX_EVENTS         = '50'
```

金鑰檔路徑長這樣：`C:\Users\你的名字\Desktop\金鑰\a-讀取.json`

**填路徑，不要把金鑰內容貼進來。** 貼內容會進到 PowerShell 的歷史紀錄，路徑不會。
程式自己去讀檔，讀完只留在記憶體裡。

`WINDOW_DAYS = 14` 表示「從今天算起兩週」。`MAX_EVENTS = 50` 是煞車：讀到超過
50 筆就停下來不做，免得一次搬太多。

**第一次跑建議先設小一點：**

```powershell
$env:CAL_PILOT_WINDOW_DAYS = '2'
$env:CAL_PILOT_MAX_EVENTS  = '5'
```

先搬兩天、最多五筆，去測試日曆看一眼對不對，再放大。

## 執行

```powershell
corepack pnpm --filter @beauessence/worker build
node apps/worker/dist/pilot/pilot-import.js
```

## 你會看到什麼

```text
批次 b1n2x9k
期間：今天起 2 天；最多處理 5 筆
1/3 讀取來源日曆（唯讀）…
    讀到 4 筆
2/3 消毒（丟掉姓名、電話、病症、地點）…
    可複製 3 筆，略過 1 筆（原因：{"all_day_unsupported":1}）
3/3 寫入測試日曆…
    已寫入 3 筆

完成。批次 ID：b1n2x9k
```

**「略過」是正常的，不是壞掉。** 常見原因：

| 看到這個 | 意思 |
| --- | --- |
| `all_day_unsupported` | 整天的事件（例如「休診」）。週曆放不下整天事件，所以跳過 |
| `multi_day_unsupported` | 跨好幾天的事件 |
| `cancelled_event` | 已經取消的預約 |
| `recurring_master` | 重複性事件的「規則」本身（實際的每一次還是會搬） |
| `outside_window` | 不在你設定的期間內 |

## 跑完之後

打開測試日曆，你應該看到幾筆「患者 A17」「患者 Q42」這樣的事件，時間跟真實日曆
對得上，但**看不出來是誰**。

## 怎麼清掉

測試日曆裡每筆事件的說明欄都寫著批次 ID（例如 `CAL-PILOT batch b1n2x9k`）。
搜尋那個 ID，把找到的事件刪掉就好。**真實日曆不用動，它從頭到尾沒被改過。**

想更徹底：直接把整本測試日曆刪掉。

## 出問題時

| 訊息 | 怎麼辦 |
| --- | --- |
| `缺少環境變數 ...` | 上面那幾行 `$env:` 有一行沒貼到，或 PowerShell 關掉重開了 |
| `來源日曆與測試日曆不能是同一本` | 兩個 ID 貼成一樣了 |
| `讀取與寫入用的金鑰檔是同一個` | 兩個路徑貼成一樣了，要用兩個不同的機器人 |
| `Source calendar read failed (403)` | 唯讀權杖沒有被授權讀那本日曆，回去檢查共用設定 |
| `Source calendar read failed (401)` | 金鑰檔無效或已被停用，回 Google Cloud 檢查 |
| `讀到 N 筆，超過上限` | 把 `WINDOW_DAYS` 調小，或把 `MAX_EVENTS` 調大 |

**錯誤訊息只會有代碼，不會有病患資料**——這是刻意的，方便你直接把訊息貼給人看
而不用擔心洩漏。

## 結束後記得清掉設定

```powershell
Remove-Item Env:CAL_PILOT_SOURCE_KEY_FILE, Env:CAL_PILOT_WRITER_KEY_FILE, Env:CAL_PILOT_PSEUDONYM_KEY
```

## 界線

- 這是**測試用**。測試日曆裡雖然沒有姓名，但它的時間仍然來自真實預約，所以**不要
  公開分享那本日曆**，只給需要測試的人。
- 這個工具**不會**把資料寫進預約系統，也不會影響任何真實預約。
- 相關治理限制見
  [CAL-PILOT-001 readiness](../integration/google-calendar-pilot-readiness.md)。
