# 事故應變 runbook

**建立日期：** 2026-07-24

**狀態：** **程序已定義，尚未演練。** 上線前必須做一次桌上演練（tabletop），
列入 Stage 6 證據包。

這份 runbook 回答三個問題：**這算不算事故？誰負責？多久之內要做什麼？**
技術上的處置步驟在各自的 runbook 裡（日曆同步、備份還原），這裡不重複。

## 1. 分級

分級決定的是**反應速度**，不是問題有多難修。

| 級別 | 定義 | 例子 | 反應 |
| --- | --- | --- | --- |
| **SEV1** | 患者資料可能外洩、或診所完全無法運作 | 未授權存取、資料庫不可用、預約全面失敗 | 立即，任何時間 |
| **SEV2** | 核心流程受損但有替代方式 | 無法建立預約但可查詢、日曆全面不同步 | 1 小時內，營業時間 |
| **SEV3** | 局部功能異常，有繞道 | 某個篩選器壞掉、死信累積 | 當個工作日 |
| **SEV4** | 不影響使用者 | 監控雜訊、非阻斷的錯誤日誌 | 排入待辦 |

**任何涉及患者個資的疑慮一律先當 SEV1。** 降級要有理由並記錄；升級不需要理由。
「先當成嚴重的、確認後降級」比反過來安全得多。

## 2. 角色

小團隊不代表沒有分工。同一個人可以兼任，但**每個角色都要有人明確承擔**，
否則會出現三個人同時在改、沒有人在對外說話的局面。

| 角色 | 職責 | 誰 |
| --- | --- | --- |
| **指揮** | 決定分級、決定做不做（例如要不要還原）、決定何時結束 | 技術負責人 |
| **處置** | 實際操作 | 工程 |
| **對外溝通** | 對診所、對患者說明 | 診所負責人 |
| **紀錄** | 記時間軸：誰在幾點做了什麼、看到什麼 | 指揮指定 |

**指揮不要自己動手。** 一旦指揮開始敲鍵盤，就沒有人在看全局了。

## 3. 流程

```text
偵測 ──► 分級 ──► 止血 ──► 溝通 ──► 復原 ──► 檢討
                    │
                    └─ 涉及個資？ ──► 隱私路徑（§5）
```

### 3.1 偵測

來源：告警、診所回報、患者回報、例行對帳。**診所回報和告警一樣重要**——目前
告警還沒接上，診所回報是主要來源。

### 3.2 分級與召集

指揮在 15 分鐘內完成分級並指派角色。SEV1／SEV2 開一個專用的溝通串，之後所有
訊息都在裡面，不散落在私訊。

### 3.3 止血優先於查因

先讓患者與診所能運作，再找原因。可用的手段：

- 開啟維護模式（`StaticMaintenanceGate`，回 `SERVICE_UNAVAILABLE`）；
- 回滾到前一個 revision（見[基礎設施與維運計畫](../architecture/infrastructure-and-operations-plan-2026-07-24.md) §7）；
- 暫停 worker 排程，避免錯誤狀態被投影到日曆；
- 櫃台改用紙本，事後補登。

**保留現場**：止血的動作不得刪除日誌、稽核或資料。需要還原時，一律還原到新的
database（[備份與還原 runbook](backup-and-restore.md) §4.3）。

### 3.4 溝通

| 對象 | SEV1 | SEV2 |
| --- | --- | --- |
| 診所負責人 | 立即 | 1 小時內 |
| 櫃台 | 立即，含「現在該怎麼做」 | 1 小時內 |
| 受影響患者 | 依 §5 判斷 | 通常不需要 |

對外訊息只說**已經確認的事**與**現在該怎麼做**。不要推測原因，不要承諾修復
時間——事故中的估計幾乎都是錯的，而錯的承諾會製造第二個問題。

### 3.5 復原

確認影響已消除、資料一致（對帳、稽核連續性）、監控回到正常，指揮才宣布結束。

## 5. 隱私事故路徑

觸發條件：**懷疑**個資被竊取、洩漏、竄改、毀損或滅失——不需要先證實。

1. **立即**：指揮同時通知診所負責人與隱私／法務負責人。這一步不等調查結果。
2. **保全證據**：稽核事件、存取日誌、當時的資料狀態一律保留，不覆蓋、不刪除。
3. **界定範圍**：哪些人、哪些欄位、什麼期間、是否已被實際存取（而非僅可存取）。
4. **止血**：撤銷憑證、關閉受影響路徑、必要時整體維護模式。
5. **通知**：個資法要求在確認侵害後，以適當方式通知當事人，說明事實與已採取的
   因應措施。**具體的通知時限、格式與是否須向主管機關報告，由診所的法務／隱私
   負責人依上線當時有效的法令認定**——2025 年修正的施行日期公布後必須重新確認
   （見[台灣隱私法規基線](../security/taiwan-privacy-legal-baseline.md)）。工程端
   不代為判斷法律義務，但必須在 24 小時內提供第 3 步的範圍認定所需的技術事實。
6. **紀錄**：事故本身、處置、通知內容與時間全部留存。

**內部升級的時間目標**（不是法定期限，是我們自己的要求）：

| 里程碑 | 目標 |
| --- | --- |
| 通知診所與法務 | 發現後 1 小時內 |
| 初步範圍認定 | 發現後 24 小時內 |
| 完整技術報告 | 發現後 5 個工作日內 |

## 6. 事後檢討

SEV1／SEV2 一律要做，**在 5 個工作日內**。

原則：**對事不對人。** 檢討要回答「什麼樣的系統設計讓這個錯誤有可能發生」，
不是「誰按錯了」。一個能被單一操作失誤搞垮的系統，問題在系統。

輸出必須包含**具體的行動項**，每一項有負責人與期限。「以後要更小心」不是行動項。

紀錄放 `docs/reviews/`，檔名 `incident-<YYYY-MM-DD>-<簡述>.md`：

```markdown
| 項目 | 值 |
| --- | --- |
| 日期 | |
| 級別 | SEV_ |
| 指揮 | |
| 偵測方式 | 告警 / 診所回報 / 患者回報 / 例行檢查 |
| 影響 | 誰、多久、哪些功能 |
| 是否涉及個資 | 是／否（是 → 附範圍認定） |

## 時間軸
| 時間 | 事件 |

## 根因

## 為什麼沒有更早被發現

## 行動項
| 項目 | 負責人 | 期限 |
```

新增紀錄後同時登進[文件索引](../README.md)的「Review record」。

## 7. 演練

上線前至少做一次桌上演練，情境建議：**「櫃台回報有患者說收到別人的預約通知」**
——它同時踩到隱私路徑、範圍認定與對外溝通，是最能檢驗這份 runbook 的情境。

演練要驗證的不是「大家知道該做什麼」，而是**「找得到人、找得到權限、找得到
資料」**：值班聯絡方式是否有效、誰有權開維護模式、稽核查得到不查得到。

## 8. 目前的限制

- **告警尚未接線**（D-010）。在那之前，偵測幾乎完全依賴診所回報與例行檢查，
  這意味著實際的偵測延遲遠大於本文件的反應時間。這個落差必須在核准會議上被
  說清楚，不能假裝流程已經完整。
- **沒有值班制度**。診所非 24 小時營運，目前也不需要；但「SEV1 立即反應」在
  營業時間外實際上做不到，這一點要由負責人明確接受或另行安排。
- **尚未演練**，因此本文件的所有時間目標都還是紙上的。
