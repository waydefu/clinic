# Worker 執行、觸發與對帳計畫（2026-07-24）

**狀態：** **設計文件，未執行。** 沒有建立任何排程器、佇列或雲端服務。

`apps/worker` 目前有的是**處理器**，不是**執行環境**：`OutboxProcessor` 已在
Emulator 驗證過領取（帶租約的交易）、外部呼叫（交易外）、結算（依
`planOutboxAttempt` 的純決策）三段分離，也有退避、死信與 `requeue`。缺的是
「誰來按下開始」、「事件被人手動改掉之後怎麼發現」，以及「補回死信要什麼權限」。

這份文件把那三件事展開成可審查的設計。實際接線受 **D-009**（日曆）與
**D-010**（雲端環境）約束。

## 1. 觸發器：拉，不是推

**設計：Cloud Scheduler 每分鐘觸發一次 Cloud Run，worker 主動拉取到期的 outbox
工作，處理完一批就結束。**

為什麼不用 Firestore 的文件變更事件直接推：

- outbox 工作有**到期時間**（退避後才重試）。推的模型只在寫入當下觸發一次，
  重試仍然需要另一個排程器——那就等於同時維護兩套。
- 拉的模型讓「積壓」變成一個可以直接量測的數字（到期但未處理的工作數），
  而推的模型只能量測「事件有沒有送到」。積壓才是我們真正想告警的訊號。
- 拉的模型天然限流：一批固定筆數，不會因為一次大量寫入把外部日曆的配額打爆。

代價是延遲下限是排程間隔（一分鐘）。對「把預約投影到日曆」這件事，一分鐘的
延遲是可接受的——日曆是投影，不是鎖（[ADR-0002](../adr/0002-calendar-is-a-projection-not-the-lock.md)）。

### 1.1 參數

| 參數 | 建議值 | 理由 |
| --- | --- | --- |
| 觸發間隔 | 60 秒 | 延遲與空轉成本的平衡 |
| 每批筆數 | 20 | 一次執行在 Cloud Run 逾時內能穩定跑完 |
| 租約 | 120 秒（`LEASE_SECONDS`，已實作） | 大於單筆最壞情況的外部呼叫時間 |
| 併發實例 | 1 | 租約已能防重入，但單實例讓積壓與配額都好推理 |
| 執行逾時 | 300 秒 | 遠大於一批的預期時間，避免半途被砍 |

**併發實例維持 1 是刻意的。** 租約機制允許多實例，但在診所規模下，多實例帶來的
是更難解釋的行為，不是更高的吞吐。要放大時，先看積壓指標再調，不要預先調。

### 1.2 至少一次，而不是剛好一次

排程觸發、Cloud Run 重試、租約過期重領——每一個都可能讓同一筆工作被處理兩次。
系統靠的不是「避免重複」，而是**重複執行是安全的**：

- 日曆事件 ID 由預約決定（`packages/domain/src/calendar-event-id.ts`，base32hex），
  同一筆預約永遠對應同一個事件；
- `upsert` 對已存在的事件是更新，`cancel` 對已取消的事件（409／410）視為成功；
- 動作依預約**當下**的狀態決定，不是工作建立時的狀態——所以延遲執行也不會把
  已取消的預約寫回日曆。

這三點都已經有 Emulator 測試覆蓋。觸發器只要不破壞它們，就不必額外去猜。

## 2. 對帳（reconciliation）

### 2.1 為什麼一定要有

outbox 保證的是「我們送出了」，不是「它現在還在那裡」。日曆是**外部系統**，
有人可以在 Google 日曆介面上直接刪掉或改動事件，我們不會收到任何通知。沒有
對帳，這種漂移會一直存在到某位患者到現場才被發現。

### 2.2 設計

每日一次（離峰時段）掃描 `calendar_links`（appointment ↔ event ID，不含 PII）
與日曆的實際內容，分三類處置：

| 漂移 | 判定 | 處置 |
| --- | --- | --- |
| **缺事件** | 預約應有事件，日曆查不到 | 重新排入 outbox（upsert），記稽核 |
| **殘留事件** | 預約已取消／完成／未到，事件仍在 | 排入 outbox（cancel），記稽核 |
| **內容不符** | 事件存在但時間或標題與預約不同 | 排入 outbox（upsert）覆寫，記稽核 |
| **孤兒事件** | 日曆上有事件，但 `calendar_links` 沒有對應 | **只告警，不自動刪除** |

最後一列是刻意的：孤兒事件很可能是診所人員自己在日曆上建立的其他行程。自動
刪除別人手動建立的東西，是這個系統最不該做的事。

### 2.3 對帳本身要能被對帳

- 每次執行寫一筆摘要（掃描筆數、各類漂移數、修復數）進稽核；
- 漂移數不是零時通知操作者——**修好了也要通知**，否則沒有人知道系統正在默默
  修補一個持續發生的問題；
- 連續三天出現同一類漂移，視為有系統性原因，升級為事故（見
  [事故應變 runbook](../runbooks/incident-response.md)）。

### 2.4 對帳不做的事

不比對患者資料。對帳只看「事件在不在、時間對不對」，日曆事件本來就採
最小欄位（不含病名、不含身分證），對帳沒有理由去讀更多。

## 3. 死信與操作者權限

死信是「重試到上限仍失敗」的工作。它不是統計數字，是一筆**沒有出現在日曆上的
預約**。

| 動作 | 誰可以做 | 要求 |
| --- | --- | --- |
| 檢視死信清單 | 管理者、櫃台 | — |
| 補回（requeue）單筆 | **只有管理者** | 必填理由，記稽核（actor、時間、理由、工作 ID） |
| 批次補回 | 只有管理者 | 需先確認外部服務已恢復；理由必填 |
| 刪除死信 | **無人** | 死信不得刪除；處理完的狀態是「已補回」或「已由人工處置並註記」 |

工作臺目前有的是合成示範（`outbox-fail-next` 與補回入口）。接上真實環境時，
權限檢查走既有的 `PERMISSIONS` 模型，與管理者刪除預約同一套（D-006 方向）。

**死信不得刪除**這一條值得說明理由：能刪除，就會有人在慌張的時候用刪除讓紅色
數字消失。留著並註記，才留得住「當時發生了什麼」。

## 4. 日曆憑證輪替

| 步驟 | 動作 | 驗證 |
| --- | --- | --- |
| 1 | 在 Secret Manager 加入新版本 | 新版本可讀 |
| 2 | 觸發一次 worker | 啟動時的金鑰型別驗證通過（必含 `client_email`／`private_key`，OAuth 用戶端會被拒） |
| 3 | 跑一次煙霧測試 | `apps/worker/src/calendar-smoke.ts` 的 upsert+cancel 成功 |
| 4 | 停用舊版本（不刪除） | 服務持續正常 24 小時 |
| 5 | 刪除舊版本 | — |

週期 90 天。**先加新版本再停用舊版本**，反過來就是一段必然的停機。步驟 3 由
負責人執行——助理不讀金鑰內容，也不代跑會在真實日曆建立／刪除事件的連線
（見 [日曆 go-live runbook](../runbooks/calendar-go-live.md)）。

## 5. 指標與告警

`apps/worker/src/worker-observability.ts` 已定義三種低基數 metric，接上後端時
直接對應：

| Metric | 告警條件 | 嚴重度 |
| --- | --- | --- |
| `CalendarAttemptMetric`（單次嘗試結果） | 失敗率 > 20%（10 分鐘） | 工作日處理 |
| `WorkerBatchMetric`（每批摘要） | 連續 3 批 0 筆完成但有待處理 | 立即 |
| `WorkerQueueSnapshotMetric`（佇列快照） | 到期未處理 p95 > 60 秒 | 立即 |
| 死信 | 出現任何一筆 | 立即 |

**低基數是硬性要求**：metric 的標籤不得包含預約 ID、患者識別或日曆事件 ID。
高基數標籤會讓監控成本爆炸，也會把識別資料洩漏到監控系統——那是一個沒有經過
隱私評估的資料出口。
