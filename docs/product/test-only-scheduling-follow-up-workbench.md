# Test-Only 排班與回診工作臺規格

**狀態：本機合成測試設計。** 本文件把工作臺與患者端的功能邊界寫成可實作、
可測試的規格；它不是診所營業時間、回診醫囑、公開病患網站或正式作業規範。
所有正式值與啟用仍受 D-001～D-006、D-011 核准約束。

## 目標與邊界

工作臺應讓授權人員配置下列內容：

1. 每週的開放星期與一日內一或多段可預約時間。
2. 指定日期的加開時段與休息／休診日。
3. 回診需求的人工確認與回診目標日期。
4. 患者端只看到本人可預約的回診選項，並建立或取消自己的回診預約。

本階段只會做雙重開關的 loopback、合成資料模型與介面。不得使用真實病患、
病歷、聯絡方式、職員身分、Google Calendar、Firebase、LINE、Meta、NAS 或公開
網址。`apps/api` 仍為唯一寫入邊界；未來 Android/iOS 也只能呼叫該 API。

## 排班資料模型

所有時間以 `Asia/Taipei` 顯示、以 UTC 保存。每筆規則都有 `scheduleVersion`、
建立／修改 actor、時間與原因代碼的稽核資料；原因不得蒐集自由文字病情。

| 模組 | 最小欄位 | 驗證與不變條件 |
| --- | --- | --- |
| 每週開放規則 | `weekday`、`startLocalTime`、`endLocalTime`、`resourceId` | 星期為 0–6；開始小於結束；同一資源同日區間不得重疊。 |
| 日期例外 | `date`、`kind` (`closed` / `extra_open`)、`intervals`、`reasonCode` | `closed` 不帶時段；`extra_open` 至少一段有效時段；不可覆蓋為另一種例外。 |
| 時段產生 | 規則版號、服務時長、容量、預約範圍 | 由 API／領域規則產生；前端與 Calendar 均不得把「空檔」當作權威。 |
| 回診決定 | `followUpStatus`、`dueDate`、`decidedBy`、`decidedAt` | 僅授權臨床／營運角色可寫；`required` 才可有 `dueDate`。 |

### 日期例外的測試用優先順序

1. `closed`：該資源該日不提供任何時段。
2. `extra_open`：在每週規則外增加明確區間；與每週規則重疊時必須先拒絕或由
   授權人員改為非重疊區間，不能自動合併。
3. 無例外：採用每週開放規則。

這是合成測試的明確、可驗證規則，並非診所正式排班決策；正式優先順序與核准
流程由 D-004 填定。

## 回診安全模型

系統的狀態只有 `unknown`、`not_required`、`required`：

- `unknown` 是預設值，患者端不可將其視為不需回診。
- `not_required` 與 `required` 必須是醫師或診所授權人員的明確決定，留下 actor、
  時間、前後狀態與規則版號。
- 系統不得依服務類型、過往預約、時間間隔或任何演算法自行推論「是否需要回診」。
- `required` 可設定一個回診目標日期；它是排程目標，不是診斷、醫囑全文或病歷。
- 取消、改期、逾期提醒與個案管理師指派均要等 D-005、D-006、D-007 核准後，
  才能成為正式功能。

## 本機測試介面

工作臺在 `TEST_ONLY_WEB_ENABLED=true` 條件下於本機提供，也可發布到已記錄的
Hosting preview channel，環境徽章會標示目前是哪一種。

**2026-07-21 調整**：預約表單改為收集姓名、電話、生日與身分證字號，工作臺與
患者端皆然。這些值只存在該瀏覽器的 `localStorage`，清單一律遮罩顯示身分證。
工作臺其餘輸入（排班時間、日期例外、帳號標籤、公告）仍不得出現病情、病歷或
薪資金額。

資料流（全部在瀏覽器內完成，沒有 API 呼叫）：

```text
患者端 -> store.js 讀取回診狀態與可預約時段
       -> store.js 建立預約、提出取消
工作臺 -> store.js 設定排班與例外、五種櫃台處置、回診確認
store  -> modules/ 的領域規則驗證、稽核、outbox 意圖、localStorage
```

正式患者網站要先完成隱私告知、身份驗證與本人資料存取（D-001～D-003、D-006、
D-011）；不能把這個測試頁公開或當作正式入口。

目前的實作允許工作臺以日期、時間與選單輸入調整排班規則，並以實際填寫的患者
資料建立預約與回診。輸入值只存在該瀏覽器的 `localStorage`，按「清除本機資料」
或清除網站資料即消失；它不會改變正式門診表或任何外部日曆。

## 驗收條件

1. 有效週規則可產生可預約時段；重疊、倒置時間與無效星期被拒絕。
2. 指定 `closed` 日期不產生時段；合法 `extra_open` 僅增加指定時段。
3. 時段保留仍透過伺服器交易／冪等規則，不能以 UI 或 Google Calendar 防衝突。
4. 回診只能由明確、可稽核的授權決定開放；患者端不能寫入決定。
5. 患者端只看合成的本人資料與合成時段，沒有個資、醫療內容或外部連線。
6. 重設測試狀態會回復固定合成基準，且不會影響任何外部系統。
7. 鍵盤操作、焦點、錯誤提示和窄螢幕布局都通過既有 UI 檢查。

## 正式上線前必填決策

| 決策 | 所屬核准 |
| --- | --- |
| 每個服務／資源的時長、緩衝、容量、開放範圍、排班與例外的建立及核准權限 | D-004 |
| 患者取消／改期與回診逾期的處理、通知與人工補救 | D-005 |
| 可設定排班、休診／加開與回診需求的角色，以及患者身分驗證 | D-006 |
| 回診個案與個案管理師指派、改派、統計規則 | D-007、D-008 |
| 隱私政策、資料保存、患者權利處理與公開網站 URL／無障礙需求 | D-001～D-003、D-011 |

每個答案需填入決策登錄的核准者、日期與證據後，才能替換合成值或啟用正式端點。
