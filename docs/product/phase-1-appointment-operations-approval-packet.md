**不可變條件：** Firestore 才是時段與防重複預約的權威來源；日曆只是一個
非同步投影。每一次保留必須用伺服器交易完成，不能靠前端顯示或日曆空檔判定。

**目前契約落差：** 瀏覽器合成原型使用複數 `itemIds`，正式 API contract/domain
仍是單一 `serviceId`/`itemId`。業主已確認正式預約允許多項，且止鼾／醫美實際
時長到診後才形成、不寫死。需先核准 published slot block、多服務占位、容量、
buffer／overrun 規則，讓每筆 reservation 有 operational interval，再一起修改
契約、domain、持久化與冪等模型；不得用服務分鐘自動相加。

### Expansion S 新角色

2026-07-28 手術／付款需求另提出會計、諮詢師／個管師、護理師與客服角色，以及
「資料範圍」和「金額範圍」分開判斷。候選矩陣已在
[Expansion S plan](2026-07-28-surgery-follow-up-expansion-plan.md#7-rbac-與欄位投影)
正規化；它沿用已核准的 D-006 身分安全基線，但臨床／金額範圍仍須 D-014、
D-015 核准。未核准前不得把這些角色加入正式 claims，也不得只在前端隱藏
金額欄位。

D-006 已於 2026-07-28 完整核准：Google＋診所自管帳號、醫師角色、櫃檯／管理者
完成到診、管理者直接刪除與多組授權碼委派、全員 MFA、自管帳號 TOTP、30 分鐘
idle／8 小時 absolute session、停權後下一個 protected request 拒絕，以及授權碼
雜湊、個別撤銷、錯誤嘗試限制。Audit 永久、append-only，任何角色不能修改或
刪除。這是 policy，不代表目前合成工作臺已成為安全邊界。

### 共通資安要求

1. 所有 staff 寫入均經 API；瀏覽器、App、LINE、Meta 與 NAS 不得直接寫入
   Firestore。
2. 每個寫入請求都需要驗證、授權、欄位驗證、冪等性與稽核。
3. 帳號建立、權限提升、停權、離職與 recovery 要有責任人與留存紀錄；未核准
   break-glass 前 fail closed。
4. D-006 的登入、MFA、session、撤銷與委派值已核准；精確 provider、recovery、
   rate-limit 參數與 service account scope 依
   [Stage 2 change plan](../architecture/stage-2-identity-and-cloud-change-plan-2026-07-28.md)
   審查，不能由程式自行推定。

## 核准後的開發門檻

Stage 0 的本機合成預約交易與權限測試已完成，不能把這份核准包寫成它們的
前置條件。D-006/D-010 已核准；Stage 2 change plan 與 deployment action 通過
審查後，才可準備 routed cloud-staging 工作。隱私 D-001～D-003 仍未核准時，
任何測試都不能改用真實資料，也不能啟用公開預約端點。
