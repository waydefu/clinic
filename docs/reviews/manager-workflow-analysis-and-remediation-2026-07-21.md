# 管理工作臺流程分析與修正紀錄 — 2026-07-21

## 結論

管理者工作臺已從「所有功能並列」整理為可執行的日常順序：

```text
今日待辦 → 預約與到診 → 排班草稿／發布 → 回診決定 → 個管指派／月度統計 → 患者端治理 → 稽核
```

這是 Phase 1 的合成資料測試工具，並非正式醫療資訊系統。所有帳號、患者、時段、稽核與日曆投影工作皆為目前瀏覽器的合成狀態；不得輸入或處理真實個資、病歷、薪資、日曆或 NAS 資料。

## 原先風險與修正

| 風險 | 修正結果 | 受影響角色 |
| --- | --- | --- |
| 工作項目無先後順序，容易先改排班而漏處理取消或回診 | 首頁加入待辦卡與固定導覽順序 | 管理者、櫃台 |
| 排班草稿會讓使用者誤以為患者立刻可見 | 發布版與草稿版同頁對照；只有「檢查並發布」會產生患者時段 | 管理者 |
| 排班變更可能破壞已成立的預約 | 發布前重新產生候選時段並阻擋影響 `confirmed`、`cancellation_requested` 預約的變更 | 管理者 |
| 櫃台看得到但不應操作治理功能 | UI 隱藏與 domain permission 兩層限制；櫃台僅能建立、取消與完成到診 | 櫃台 |
| 回診被誤當成系統推論 | 僅允許授權管理者針對完成到診逐筆記錄「需要／不需要」及目標日期 | 管理者 |
| 個管工作量無法支援月度核算 | 以「個管師 × 臺北月份 × 不重複患者」計算，同時顯示完成到診與合成 credit 次數 | 管理者 |
| 患者端公告與維護可能誤傷預約 | 維護操作要求確認，支援開始／恢復時間；生效時完整切換為維護畫面 | 管理者 |
| 將來接外部服務時容易把 side effect 寫進 UI | 預約狀態變更只產生 audit 與 outbox 意圖，不會直接呼叫 Calendar、Firebase DB 或 NAS | 開發者 |

## 角色工作流

### 管理者

1. 從首頁先處理取消待確認、尚未決定的回診與未指派個案。
2. 在預約區建立、取消或完成合成到診。
3. 在排班區調整草稿、檢查影響後發布。
4. 只對已完成到診進行逐筆回診決定。
5. 指派個管師，檢視本月不重複患者、完成到診與合成 credit。
6. 管理合成帳號、患者公告、維護模式與發布紀錄。
7. 在稽核區追蹤操作和日曆投影意圖。

### 櫃台員工

1. 建立合成預約，或完成／取消既有合成預約。
2. 不能看到或修改排班、回診、個管、帳號、公告、維護或發布紀錄。
3. 權限限制不只依賴畫面隱藏；command adapter 也會檢查動作權限。

### 患者端

1. 僅顯示已發布的時段。
2. 回診預約只有在該合成患者具有授權的 `required` 回診決定時可進行。
3. 取消動作先成為取消待確認；完成到診不可由患者端取消。
4. 維護模式生效時不顯示預約流程。

## 模組化設計落點

| 需求 | 程式邊界 |
| --- | --- |
| 角色與動作授權 | `modules/permissions.js` |
| 排班、例外日期、時段與發布影響 | `modules/schedule-engine.js` |
| 預約、取消、完成到診與回診決定 | `modules/appointment-domain.js` |
| 個管指派、月度工作量與待辦 | `modules/case-management.js` |
| 公告、維護、帳號與發布紀錄 | `modules/workspace-domain.js` |
| 合成資料 schema 與 adapter | `modules/state-schema.js`、`staging-store-v2.js` |
| 管理者呈現與事件協調 | `modules/admin-view.js`、`admin-bootstrap.js` |
| 患者端流程 | `patient-app-v2.js` |

完整模組與未來 API／App／NAS 替換方式見 [Synthetic Web modular architecture](../architecture/synthetic-web-modular-architecture.md)。
