## 429 結果（FAIL）

- 端點：tag `POST /v1/return-lookup`，固定一組不存在的合成查詢值，未登入。適用政策 `lookup_or_auth_failure`（15 分鐘內 5 次失敗，第 6 次鎖 15 分鐘）。
- 每次請求帶一個不同的偽造最左 `X-Forwarded-For`（`198.51.100.0/24` 文件網段）。
- 第 1–3 次都回 `404 NOT_FOUND`。`rate_limit_state` 出現 3 個不同的 key，每個的 IP 部分都是該次的偽造值，count 各為 1。
- 判定：身分碎裂，依規則在第 3 次停止（預算 20，用掉 3）。limiter 紀錄讓它自然過期，沒有清除。

### 根因（CONFIRMED）

`deriveClientIp`（`apps/api/src/platform/runtime/client-ip.ts`）取 `X-Forwarded-For` 由右數第 `TRUSTED_PROXY_HOPS` 個值。這個設計假設請求一定經過 Hosting，Hosting 會多加一層。但 `internal-test-api` 是 `ingress=all`，而且 `roles/run.invoker` 給了 `allUsers`，任何人都能繞過 Hosting 直接打 `*.run.app`。這時只有 Cloud Run 前端加一層，由右數第 2 個剛好就是客戶端自己送的值。

目前 100% 的 `internal-test-api-p109durable1` 也有同樣問題：`client-ip.ts`、限流器與 `return-lookup.controller.ts` 從 `caaa69e` 到 `6cf9a5a` 都沒改過。這是既有曝險，不是這次部署造成的。

### 需要決策（未實作）

修正會改變限流的身分定義，這屬於政策選擇，必須先記入決策登記簿：

- 讓 Cloud Run 只能經由 Hosting 或負載平衡器進入。要先確認 Firebase Hosting rewrite 在受限 ingress 下是否可用。
- 限流改看無法偽造的前端資訊，例如在負載平衡器上加一個伺服器端才能設定的 header。
- 另加一個只以查詢身分計數的 bucket。這能擋住針對單一身分的暴力查詢，但別人也能藉此故意鎖住某位病患的查詢。
