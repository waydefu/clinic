# 診所療程卡影像修復交接紀錄（2026-08-07）

四張療程卡的圖片在建置階段被置中裁切切掉內容，最嚴重的一張丟掉 63.4%，
「止鼾好眠牙套」被切成「子眠牙套」。本輪修掉它，並補一道 fail-closed 門檻
讓同類問題不會再無聲發生。

上一輪（[2026-08-06 官網併回 design system](2026-08-06-clinic-site-design-system-convergence.md)）
把這件事標為「沒修，因為修法是內容決定」。查證後那個判斷只對一半——四張裡有三張
不需要任何內容決定。

## 影響範圍

只改素材、內容資料與建置腳本。沒有動後端、Rules、API contract、RBAC、`packages/domain`。
沒有新增表單欄位。沒有新增執行期依賴。字型預算維持 0 KiB。影像預算**未調整**
（實際用量反而下降）。

## 一、根因

`build-clinic-assets.mjs` 對療程卡套 `aspect: 4/3` **置中裁切**。這對人像、器械、
環境照是安全的，但這四張的素材性質不同：

| 素材 | 原圖 | 實際是什麼 | 置中裁切丟掉 |
| --- | --- | --- | ---: |
| `service-snoring.png` | 1024×281（3.64:1） | 五欄資訊圖：5 個成因＋8 個子項 | **63.4%** |
| `service-turbinate.jpg` | 2560×1440 | 行銷投影片：標題＋內文在左、插圖在右 | 25% |
| `service-septoplasty.jpg` | 2560×1440 | 同版型 | 25% |
| `service-mouthguard.webp` | 2560×1440 | 同版型 | 25% |

結果：「下鼻甲手術」→「鼻甲手術」、「鼻中隔手術」→「中隔手術」、
「好眠牙套」→「**子眠牙套**」（「好」的左偏旁 `女` 落在裁切線外）、
止鼾五合一只剩中間一欄「咽喉結構異常」。

**腳本自己早就寫好了正解，只是沒有人套用：**

> 若日後有主體偏一邊的圖，要在 `TARGETS` 裡補一個明確的裁切框，而不是把這裡改成
> 某種自動偵測——猜錯的裁切比沒裁還糟。

### 為什麼每一道 gate 都是綠的

`check:tokens` 讀 CSS、`typography.spec.ts` 量 DOM 的 computed style、
axe 掃可及性樹。**沒有任何一道會打開 WebP 看裡面寫了什麼。**
`alt="止鼾五合一療程示意"` 在所有自動化檢查眼中都是合格的替代文字，
即使畫面上只剩一個症狀分類。

上一輪把官網字級併回系統、低於 14px 的文字歸零——量的是 HTML 元素。
**這批文字根本不是 HTML。**

## 二、順帶查出的兩件事

**1. 投影片的文字與卡片自己的 HTML 重複，而且不一致。**

| 卡片 HTML | 投影片烘焙的文字 |
| --- | --- |
| `title: '下鼻甲手術'` | 下鼻甲手術 |
| `title: '止鼾好眠牙套'` | **好眠牙套**（少了「止鼾」） |

**2. 五合一資訊圖的桌機版與手機版對成因的編號順序不一致**（官網同時存在兩份）：

| # | 桌機版 2600×714（2024/11） | 手機版 930×1067（2024/12） |
| ---: | --- | --- |
| 2 | 鼻結構異常 | **下巴短厚** |
| 3 | 咽喉結構異常 | **鼻結構異常** |
| 4 | **下巴短厚** | **咽喉結構異常** |

同一份衛教內容有兩個編號版本，沒有任何機制會發現它們分歧。**圖片不是可維護的
內容來源**——這本身就是不要把資訊放進圖片的理由。

依使用者 2026-08-07 裁示，HTML 版以**桌機版順序**為準。

## 三、處置

依素材性質分兩種，不是一套裁切參數打天下。

### 三張投影片：裁到只取插圖

在 `TARGETS` 補 `focus: { cx, cy, halfW }`。左界的決定條件是量出來的：
內文最右緣 turbinate 在 `x≈0.560`、mouthguard 在 `x≈0.635`，裁切框左界必須大於它。
**第一次試裁沒守住這條，兩張都漏出殘字**（「織」的一角、「置」），第二輪修正後才乾淨。

投影片上的標題與內文本來就與卡片的 `title`／`subtitle` 重複，拿掉之後文字回到 HTML。

### 止鼾五合一：內容搬進 HTML

整張都是資訊，沒有插圖可取。五個成因與八個子項搬進 `NASAL_SERVICES` 的
`sections`，成為 `<h2>` ＋ `<ul>`（**文案一字未改**）。沿用既有的
`heading`／`paragraphs`／`bullets` 結構，**渲染器完全沒改**——子項以
「鼻結構異常：鼻中膈彎曲、下鼻甲肥厚、過敏性鼻炎」的形式併進同一列。

卡片圖改用官網「打鼾嚴重的常見症狀」（`內文圖1.jpg`，3840×2160）裡的側睡人物插圖，
同樣只取插圖。原 `service-snoring.png`（sha256 `69d04fee…1e407e`）已不再被任何
target 引用，同日移除；內容以 `clinic-content.js` 為準，原圖可由 git 歷史取回。

### 四張 `alt` 改寫

原本描述的是整張投影片，現在只描述插圖：

| 檔案 | 新 alt |
| --- | --- |
| service-snoring | 側躺睡眠時張口呼吸的示意插圖 |
| service-turbinate | 鼻腔內部結構的示意插圖，標示下鼻甲位置 |
| service-septoplasty | 兩人夜間安穩入睡的示意插圖 |
| service-mouthguard | 止鼾牙套裝在上下排牙齒上的器械示意插圖 |

## 四、新增的 gate（本輪的長期價值）

`build-clinic-assets.mjs` 的 `MAX_BLIND_DISCARD = 0.12`：

> 置中裁切會丟棄超過來源面積 12% 時，該 target **必須**宣告 `focus`，否則建置失敗。

門檻不是理論值，是照現況資料訂的——讓兩張醫師照（丟 4.3%／8.9%，本來就正確）
留在線下，讓四張療程圖（丟 25%～63.4%，本來就壞掉）落在線上。

**注入測試（2026-08-07 實跑，注入不進 commit）：** 暫時拿掉 turbinate 的 `focus`，
建置轉紅並印出：

```
Error: service-turbinate.webp: 置中裁切會丟掉來源的 25.0%（上限 12%）。
  來源 2560×1440（比例 1.78:1），目標比例 1.33:1。
  這代表主體不可能同時留在畫面裡。請在 TARGETS 的這一筆補上 focus：
    focus: { cx: 0.5, cy: 0.5, halfW: 0.25 }  // 依實際主體位置調整
```

還原後建置恢復正常。另補一項非阻斷警告：輸出寬度低於目標寬度時提示來源解析度不足
（舊的 snoring 輸出 375px < 540px，正是這種情況）。

## 五、實測結果

| 檔案 | 前 | 後 | 變化 |
| --- | --- | --- | ---: |
| service-snoring.webp | 375×281／8 360 B | 540×405／8 842 B | 解析度 +44% |
| service-turbinate.webp | 540×405／14 726 B | 540×405／4 826 B | **−67%** |
| service-septoplasty.webp | 540×405／15 154 B | 540×405／12 374 B | −18% |
| service-mouthguard.webp | 540×405／15 786 B | 540×405／9 572 B | −39% |
| 四張小計 | 54 026 B | 35 614 B | **−34%** |

瀏覽器實測（`http://127.0.0.1:3100/clinic`，1280×900 與 375×812）：
四張 `naturalSize` 皆 540×405，CSS box 266×200，比例完全相同，
**`object-fit: cover` 不再裁掉任何東西**。四欄節奏不變。零 console error。

詳情頁 `/clinic/nasal/snoring-five-in-one`：新的「打鼾的五個常見成因」渲染為
`<h2>` ＋ `<ul>`，五個 `<li>` 的 computed `font-size` 皆 **16px**（符合 R-6），
標題層級與既有四節一致。

## 六、規則書更新

新增 **R-26　資訊不得只存在於圖片像素裡**，綁六份權威依據：
W3C SC 1.4.5（規範性；本案不適用 essential 例外，因為這些內容用 HTML 完全可以呈現）、
W3C WAI Complex Images、GOV.UK Design System、Material Design 3 Cards、
Apple HIG Accessibility（200%／Dynamic Type）、MDN Responsive images。
R-6 補上一句說明它只管得到 HTML 文字並指向 R-26；§7.2 記錄本次複核。

**查過但沒有採用的：** 小米（HyperOS）與 ROG（ASUS）都沒有公開發布可引用的設計系統
規範——HyperOS 只有「Alive Design」品牌論述，ROG 是視覺識別而非設計系統。
它們的產品頁確實大量使用文字烘焙的行銷主視覺，但都另有真實 HTML 標題承載同一資訊。
**沒有把「大公司也這樣做」寫成依據**，那會製造第二套權威。

## 七、沒有做的事

- **線上 WordPress 官網沒有動。** 那是另一套前端。查證時發現線上站的療程圖
  **全部 `alt=""`**，且「打鼾嚴重的常見症狀」「治療流程圖」兩張複雜圖同樣只有像素、
  沒有文字替代。這不在本 repo 範圍，但值得另外告知診所。
- **視覺基線沒有重拍。** `capture:ui` 會覆蓋 `docs/reviews/assets/ui-visual-baseline-2026-08-06/`，
  重拍是獨立決定（比照上一輪的處置）。**但要注意：該基線的 `/clinic` 相關 PNG 現在
  已與畫面不符**——四張卡片圖都換了。`check:structure` 仍是綠的，因為它驗的是
  manifest 與磁碟檔案的 SHA-256 一致性，不是基線與現況一致性。下一位若要重拍，
  這是原因。
- **非字級 `clamp()` 的 24 處仍免檢**（上一輪的後續項目，本輪未處理）。
- **麵包屑的三個語意偏離**（非 `<ol>`／`<li>`、缺 `aria-current="page"`、`/` 是真實
  文字節點）仍未修。
- **規則書 §5.3 的實體裝置矩陣**仍然全部欠著；本輪同樣沒有實體裝置存取權。
- **200% 文字放大與報讀器實測**：R-26 的驗證欄要求這兩項，本輪只做到自動化與
  瀏覽器量測，人工驗收留給下一位。
