# 工作臺分頁與日曆投影（2026-07-22 第四輪）

## 範圍

專案負責人指定的五件事：工作臺分頁化、預約清單修改備註、回診卡順手指派個管
師、假日曆補完 Google 語意、手機版版面與患者行事曆匯出調整。

## 一、工作臺分頁

七個工作區改為一次只顯示一個（`modules/workspace-tabs.js`），以
`location.hash` 路由。**評估後不採用 History API 路由**——它需要在
`firebase.json` 與 `server.mjs` 各加一份改寫規則，兩邊漂移就會出現「子頁重新
整理變 404」；而換來的 URL 美觀與 SEO 在全站 `noindex` 的內部工具上沒有價值。
完整對照與「唯一會改口的觸發條件」記於
[模組化架構文件](../architecture/synthetic-web-modular-architecture.md)。

分頁可見性與權限的判斷**集中在一處**：bootstrap 標記 `data-restricted`，
`hidden` 一律由分頁模組決定。兩邊各自寫 `hidden` 會互相蓋掉，櫃台帳號帶著
`#schedule-section` 進來會看到空白頁而不是退回營運首頁。

## 二、預約清單：修改備註

處置選單旁一鍵展開。備註是營運註記而非臨床決定，因此
`updateAppointmentNotes` **不改狀態、不釋出時段、不產生日曆投影**，但**寫
稽核**（`appointment_notes_updated`）。已取消／未到的預約不再開放修改。

## 三、回診卡：順手指派個管師

回診確認卡新增可選的個管師欄位，呼叫**與「個案管理」分頁相同**的
`assignCaseManager` 與相同的稽核事件，留空表示維持現有指派。

安全細節：該路由**另外檢查 `MANAGE_CASES`**。在方便的地方順手做，不代表可以
繞過那個動作的授權——目前兩者都是管理者權限，但這個檢查必須是明確的，否則
日後角色細分時會變成無聲的權限提升。

## 四、日曆投影

### event ID 綁預約，不綁狀態

原本每個狀態各自算出不同的 event ID，等於每個狀態在日曆上開一格新的。實測
一筆預約走完生命週期：

```text
舊：建立 → 1 個事件；改期 → 2；到診 → 3；取消 → 仍然 3
新：建立 → 1 個事件；改期 → 1；到診 → 1；取消 → 0
```

取消刪不掉任何一個，因為它去刪的是「取消專用」的 ID，那格從來沒被建立過，
於是回報「找不到＝成功」。409／410 冪等與「依執行當下狀態選動作」的機制本身
是對的，**錯的是鍵的粒度**。理由與被否決的替代方案見
[日曆 event ID 文件](../architecture/calendar-event-id.md)。

> 測試教訓：原本的取消測試沿用同一筆工作只改狀態，**驗證了機制卻沒驗證
> 接線**，缺陷正是躲在這個縫隙。現已改為走真實的兩筆工作流程，並新增
> 「建立→改期→到診→取消後日曆為空」的完整生命週期斷言。

### 假日曆的 Google 語意

| Google 回應 | 處理 |
| --- | --- |
| 409（事件已存在） | **冪等成功**，改為更新內容 |
| 410／404（要刪的事件早已不在） | **成功**，目標狀態已達成 |
| event ID 格式不合 | **不可重試**，直接死信 |

動作依**執行當下**的預約狀態決定，不是排入時的狀態：工作可能等退避結束才
執行，期間預約已被取消，這時再把事件寫回日曆就是錯的。

## 五、手機版面與行事曆匯出

- 44rem 斷點把帳號治理、月度統計、事件、排班比較設為 2 欄；到 375px 每欄只剩
  約 156px，表單欄位（實測 227px）溢出容器。已在 ≤30rem 收成單欄。週次選擇
  維持 2 欄——短標籤放得下。
- 患者與診所的行事曆事件刻意不同：

| | 患者自己的行事曆 | 診所端投影 |
| --- | --- | --- |
| 時間 | 只標記開始時間（`DTSTART` 無 `DTEND`，RFC 5545 §3.6.1） | 開始到結束一小時 |
| 顏色 | `COLOR:green`（RFC 7986，**盡力而為**） | Google `colorId` 綠色 |
| 提醒 | 前一天同一時刻（`TRIGGER:-P1D`） | 由診所日曆自身設定 |

顏色的支援度誠實說明：Apple 行事曆等部分用戶端會採用，**Google 匯入 .ics 時
會忽略 `COLOR`**。因此顏色只當加分，不得用來承載必要資訊。
