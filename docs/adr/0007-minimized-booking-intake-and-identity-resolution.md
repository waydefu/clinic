# ADR-0007：最小化預約欄位與身分辨識規則

**狀態：** 已接受（依業主決定 `BOOKING-MINIMIZATION-2026-09-22`）
**日期：** 2026-09-28

## 背景

業主於 2026-09-22 決定新預約只收姓名、電話、月日生日與國籍（本國／外國），
不再收身分證、護照、來源渠道、介紹人與攜帶健保卡意向，也不新增 OTP 或其他
替代身分因子（見[決策登記](../product/phase-1-decision-register.md)）。原本用身分
證辨識同一人；拿掉之後必須重新定義「是不是同一個人」，而且不能靠猜。

本 ADR 只固定技術映射，不改業主的欄位決定。它延續
[ADR-0005](0005-patient-intake-and-appointment-command-are-separate.md) 的邊界：
身分辨識屬於 intake，預約指令仍只拿 opaque `patientId`。

## 決定

### 欄位

| 欄位 | wire 形狀 | 用途 |
| --- | --- | --- |
| `name` | 字串，1–30 字 | 顯示；同候選時比對姓名 |
| `phone` | 8–20 位數字（可含分隔符） | 身分比對鍵的一半 |
| `birthDate` | `--MM-DD`（XSD gMonthDay） | 身分比對鍵的另一半；閏日以 2000 年驗證 |
| `nationality` | `domestic` \| `foreign` | 只給櫃台看的這次到診資訊 |

`PatientIntakeSchema` 與 `ReturnLookupRequestSchema` 皆為 strict；夾帶已移除的
欄位（`nationalId`、`passportNumber`、`hasNhiCard`、`sourceTags`、`referrerName`）
一律拒絕，不默默丟棄。

國籍記在預約的 `intakeNationality`，不進身分比對鍵、查詢、候選選人、audit、
outbox、Calendar 投影或匯出。員工讀全診所預約清單時會帶出這個值給工作臺顯示
（2026-09-28 補充）；病患以回診 session 讀自己的清單時不帶，與 `patientId` 相同。

### 身分辨識

比對鍵是電話數字加月日生日，姓名不進鍵。同一個鍵底下可能有多位病患，所以
索引存的是病患 ID 清單，並放在新的索引集合；舊的單值索引保持原狀、不改寫。

| 候選人數 | 新預約 | 回診查詢 |
| --- | --- | --- |
| 0 | 建立新病患 | 通用查無 |
| 1，姓名相同 | 沿用該病患 | 建立回診 session |
| 1，姓名不同 | 拒絕（`PATIENT_IDENTITY_AMBIGUOUS`，HTTP 409） | 建立回診 session |
| ≥ 2 | 拒絕 | 通用查無 |

姓名比對前做 NFKC、去頭尾空白、合併連續空白與轉小寫。建立與沿用在同一個
transaction 內讀索引、讀候選、寫索引，並行的同一人請求會收斂成一位病患。

拒絕訊息不說明原因，也不透露候選人數或任何人的資料，只請患者改為來電。

### 舊資料

- 只剩舊 hash 的紀錄不反推年份、不與新預約合併，也不批次清除。
- 舊紀錄上的證件、健保卡意向與來源標籤只供工作臺顯示；證件維持遮罩。
- 瀏覽器端合成狀態中的舊完整生日在回診查詢時以月日比對，同樣受「恰好一位」
  規則約束。

## 後果

- 同電話、同月日、不同姓名的兩個人（例如家人共用電話）無法線上預約第二位，
  必須由櫃台協助。這是刻意的 fail closed，不是缺陷。
- 新舊索引並存；舊索引不再被寫入。是否清理由之後的資料保存決定處理，不在此。
- 這是 breaking payload 變更：舊版前端送出的證件欄位會被 API 拒絕，所以 API 與
  網頁必須同一個 PR 合併、同一次部署。回退時兩者一起回退；新索引裡的資料對舊版
  程式無害（舊版只讀舊索引）。

## 替代方案

- **把姓名放進比對鍵：** 拒絕。同一人換寫法就會被當成新病患，重複病患會悄悄
  增加，而且看不出來。
- **同鍵多候選時用姓名挑一位：** 拒絕。沒有第二個因子時，同名同生日共用電話
  無法區分，猜錯就是把預約掛到別人名下。
- **新增 OTP 或其他驗證因子：** 業主明確不採用。
