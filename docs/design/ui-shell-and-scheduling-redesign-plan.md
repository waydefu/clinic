# App Shell 與日程工作區重構規劃

**狀態：** plan-only 設計規劃。不改變目前 Stage，不啟用任何路由。

**撰寫日期：** 2026-08-04

**與既有設計文件的關係：** [Boutique Clinical Command](boutique-clinical-command-2026-07-25.md)
的六個階段（Design Tokens 2.0、瑞士資訊骨架、工作臺表格化、情境式指揮中心、品牌層、
Motion System）**已全部完成**。本文件**不重做**那六個階段，只涵蓋它們沒有處理的兩塊：
**全域 App Shell** 與 **日程管理工作區**。

[介面規則書](ui-ux-rules.md) 是 binding 規則，本文件的任何設計都不得牴觸它。

| # | 問題 | 證據 |

## 2. 新資訊架構

### 2.1 導覽分組

初診、回診、醫美、手術**不各自佔用最高層導覽**，而是作為日程事件的**類型**與**篩選
條件**。這是本規劃最重要的一個結構決定：服務線會持續增加，導覽不能跟著長。

```
日常營運
├── 今日工作臺        ← 預設進入點
├── 日程管理          ← 核心工作區
├── 病患管理
└── 待辦與通知

營運與帳務            ← 整組受 D-015 阻擋
├── 付款與款項
└── 營運報表

管理設定
├── 營業時間管理
├── 員工與權限
├── 系統整合
└── 稽核紀錄
```

每個導覽項宣告所需 permission，未授權者不顯示**且**直連 URL 被 router guard 擋下。
只做前者是 P4 那類問題的溫床。

### 2.2 桌面版 App Shell

```
┌────────────────────────────────────────────────────────────┐
│ [品牌] [全域搜尋            ] [分院▾] [◍同步] [🔔] [使用者▾] │
├──────────┬─────────────────────────────────────────────────┤
│ 日常營運  │                                                 │
│  今日     │                                                 │
│  日程 ◀   │              主工作區                            │
│  病患     │                                                 │
│  待辦     │                                                 │
│ ──────── │                                                 │
│ 營運帳務  │                                                 │
│ ──────── │                                                 │
│ 管理設定  │                                                 │
└──────────┴─────────────────────────────────────────────────┘
```

- **分院切換**：P6 才有實際資料，P1 先建立 UI 位置與單一分院的預設值，避免日後
  插入時整條 header 重排。
- **同步狀態**：Google Calendar 同步狀態常駐可見（已同步／同步中／同步失敗）。
  失敗必須同時有圖示與文字，不只顏色。
- **手機版**：左側導覽改為抽屜（drawer），詳見 [行動版 UX 規劃](mobile-ux-plan.md)。

### 2.3 患者端獨立 Shell

患者端與工作臺**分離建置入口**，不只是分離路由。目標是 `check-web-ui.mjs` 這類守衛
能明確知道自己在守哪一邊，不會再發生 P4。

患者端頁面：下一次預約（首頁）、預約紀錄、改期／取消申請、回診與術前提醒、通知、
個人資料、表單與文件。**不得出現**任何內部工作臺入口、測試工具、金額管理或系統設定。

## 3. 日程管理工作區

### 3.1 檢視模式

| 模式 | 桌面 | 手機 |
| --- | --- | --- |
| 日 | ✔ | ✔ |
| 週 | ✔ 預設 | 可切換，非預設 |
| 月 | ✔ | ✔ |
| 清單 | ✔ | ✔ **預設** |

**手機預設為當日清單**，不強迫使用七欄週曆——這是負責人明確要求，也符合
[介面規則書](ui-ux-rules.md) 對窄版重排的規定。

### 3.2 篩選維度

分院、醫師、諮詢師、個管、房間、設備、事件類型。篩選狀態必須進入 URL，否則櫃檯
無法把「今天張醫師的手術」這個視角傳給同事。

### 3.3 互動

- **拖曳改期**：放開時先做衝突檢查，再送出。失敗必須把事件**動畫退回原位**並就地
  說明原因，不可只跳 toast——櫃檯的視線在事件上，不在螢幕角落。
- **衝突提示**：見 §5 衝突規則。衝突以紅色**加圖示加文字**呈現。
- **右側 Drawer**：點擊事件開啟，不換頁。桌面版 Drawer 不遮蔽日曆的當日欄位。

### 3.4 詳細資料 Drawer

由上而下：病患基本資料、預約類型與狀態、醫師／諮詢師／個管、日期時間與資源、
療程或手術資料（D-014）、麻醉方式（D-014）、費用與付款（D-015）、Google Calendar
同步狀態、備註、活動與稽核紀錄。**底部固定操作列**，滾動時不消失。

受決策阻擋的區塊在核准前**不顯示為空欄位**，而是整區不存在。空欄位會讓使用者以為
資料遺失。

## 4. Design Tokens

現行 tokens 由 `pnpm check:tokens` 守衛（[`scripts/check-design-tokens.mjs`](../../scripts/check-design-tokens.mjs)）。
本節為**擴充**，既有 token 不重新定義。

### 4.1 事件類型色

負責人指定的四色，依 §1.1 的定位調整命名——主要服務線是鼻功能與睡眠呼吸：

| 事件類型 | 色相 | Token |
| --- | --- | --- |
| 初診 | 藍 | `--event-first-visit` |
| 回診 | 紫 | `--event-follow-up` |
| 手術 | 深玫瑰／酒紅 | `--event-surgery` |
| 醫美 | 粉紅 | `--event-aesthetic` |

`--event-aesthetic` 在醫美服務線啟用前**不得**出現在任何介面；token 先定義是為了讓
色彩系統一次算完對比，不是授權使用。

### 4.2 狀態色（與事件類型**完全分離**）

| 狀態 | 色相 | 必要的非顏色訊號 |
| --- | --- | --- |
| 已確認 | 綠 | 文字「已確認」 |
| 待確認 | 黃 | 文字「待確認」 |
| 已取消 | 灰 | 刪除線＋文字 |
| 衝突 | 紅 | ⚠ 圖示＋文字 |
| 同步失敗 | 紅 | 警示圖示＋文字 |
| 同步中 | 藍 | 旋轉指示器＋文字 |
| 已同步 | 成功色 | ✓ 圖示 |

**事件類型與狀態不得共用色票。** 一個粉紅色的醫美預約被取消時，它是灰的還是粉紅的，
必須有明確答案：**狀態壓過類型**，取消的事件一律灰色，類型改以左側色條保留。

### 4.3 不得只靠顏色

所有狀態必須同時具備文字、縮寫或圖示。這條已是 [介面規則書](ui-ux-rules.md) 的既有
規則，也由 `forcedColors: active` 的 Playwright 預檢守住。

### 4.4 其他 token 群組

品牌色（既有，含香檳金＝Brand Decorative Accent，永遠不代表狀態）、中性色、文字階層、
間距、圓角、陰影、表格密度（緊湊／標準）、按鈕高度（44px 觸控基準）、Drawer／Dialog／
Sheet 規格、桌面與手機斷點。

**香檳金的既有約束不得放寬**：它只承載品牌與質感，永遠不代表狀態、選取、焦點或
可點擊。`check:tokens` 已有守衛擋它流入狀態或互動元件。

### 4.5 整體風格

專業、安心、高資訊密度但清楚。暖白或淺灰背景、深灰藍文字、低陰影。避免過度玻璃
擬態、漸層、大片粉紅及行銷網站式留白——工作臺不是官網。

## 5. 衝突規則（P4 階段實作，D-014 阻擋）

| 規則 | 說明 |
| --- | --- |
| 同一醫師不得重疊 | — |
| 同一病患不得重疊 | — |
| 同一手術室不得重疊 | — |
| 同一設備不得重疊 | — |
| 全身麻醉需檢查麻醉資源 | 麻醉人員與設備皆須可用 |
| 改期保留原始紀錄 | 不覆寫，寫入新版本並保留稽核鏈 |
| 取消不得直接刪除資料 | 刪除是清掉看診事實；取消是狀態轉換 |

最後兩條與現行 domain 的既有語意一致（roadmap 2026-07-25：「取消回診才是撤銷回診的
正確方式，刪除是清掉整筆看診事實」），實作時應沿用 `packages/domain` 既有的狀態機，
不另建一套。

**初診與回診在時鐘上重疊是刻意的**（roadmap §四）：診所人力足以並行兩條線，容量以
「人力線」計算而非「時鐘分鐘」。衝突檢查不得把這兩個時段格改為互斥。

## 7. 頁面 migration 順序

漸進式，每一步都可獨立回滾：

1. **Shell 並存**：新 AppShell 與舊 header 以建置開關並存，預設仍為舊版。
2. **單頁試點**：「今日工作臺」先切到新 Shell，其餘頁面不動。
3. **逐頁遷移**：病患管理 → 待辦 → 管理設定。每頁遷移後跑一次視覺基線。
4. **日程工作區**：新頁面，不取代既有週曆；兩者並存直到功能對等。
5. **移除舊 Shell**：所有頁面遷移完成且視覺基線通過後才移除開關。

**任何一步都不刪除既有可用功能。** 第 5 步之前，舊 Shell 隨時可切回。

---

## 8. 驗收條件

1. 所有主要頁面套用同一 App Shell。
2. 手機 320px 以上無雙向捲動（既有 `mobile-layout.spec.ts` 已守住，遷移後必須續綠）。
3. Header、通知與帳號位置在所有頁面一致。
4. 可透過建置開關切換舊版與新版 Shell，便於回滾。
5. 櫃檯可在單一畫面完成日常排程，不需在多個頁面往返。
6. 所有改期與取消都有稽核紀錄。
7. 手機版可完成新增、查看與改期。
8. `check:tokens`、`check:ui`、`affordance.spec.ts`、`theme.spec.ts` 全綠。

## 9. 風險

| 風險 | 影響 | 緩解 |
| --- | --- | --- |
| Shell 並存期間兩套樣式互相污染 | 中 | 新 Shell 樣式全部加前綴命名空間；`check:ui` 新增守衛 |
| 日程工作區與既有週曆功能分歧 | 中 | 兩者共用同一份 `schedule-engine.js`，不複製邏輯 |
| 患者端分離建置入口導致資產重複 | 低 | 共用 token 與 domain vendor，只分離 Shell 與頁面樣式 |
| 拖曳改期在觸控裝置上誤觸 | 中 | 手機版預設不啟用拖曳，改用明確的「改期」動作 |
