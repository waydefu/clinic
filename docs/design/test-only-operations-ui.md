# 工作臺與患者預約 UI／UX

## 適用範圍

本文件規範 `apps/web/public` 的測試版本。它可在本機旗標下運行，也可發布到已記錄的 Firebase Hosting preview channel。所有狀態僅存在目前瀏覽器的 `localStorage`，沒有後端、資料庫或登入系統。

D-001～D-011 尚未核准，因此本頁的政策、角色與文字都不得被推定為診所已核准的正式規則。

## 資料範圍（2026-07-21 依專案負責人決定調整）

患者端**會收集**姓名、電話、生日（西元）、身分證字號與健保卡欄位；身分證是「同一人同時只能有一筆未完成預約」的識別依據。

這些值只存在**訪客自己瀏覽器的 `localStorage`**，不會傳送或保存於診所。這與早期「只用不透明合成 ID」的設計不同，該決定與其緩解措施記錄於[決策登錄](../product/phase-1-decision-register.md)。

緩解措施（不得回退）：

- 清單一律以 `maskNationalId` 遮罩顯示（`A12****789`），`check:ui` 會驗證這一點。
- 患者端必須明示「資料只會保存在我這台裝置的瀏覽器」。
- 欄位採允許清單，新增任何欄位都必須是刻意的決定。
- D-001～D-003 核准前，不得以此預覽蒐集真實病患資料作為營運用途。

## 角色與最小權限

| 視角 | 可使用功能 | 不可使用功能 |
| --- | --- | --- |
| 主管（模擬） | 所有合成營運功能：營業時間與例外、預約處置、回診決定登錄、個管首次指派與改派、員工權限、公告、維護模式、進階設定、稽核紀錄 | 真實登入、正式授權、外部整合 |
| 櫃台員工（模擬） | 建立／取消／改期預約、標記未到／到診、依醫師指示登錄回診決定、首次指派個管師、查看非金額個管工作量 | 營業時間設定、個管改派、員工權限、公告與維護設定、進階設定、稽核紀錄 |
| 患者 | 選擇初診或已確認的回診、選項目、選時段、填基本資料、提出取消、匯出行事曆 | 直接取消（須櫃台確認）、查看他人資料、任何治理功能 |

目前的角色選單只用於 UX 與最小權限驗證，**不是 Authentication**。正式版必須由後端驗證身分與角色，不能只依賴前端隱藏控制項。

## 工作臺功能契約

1. 每週排班可一次選取多個星期，並為每批星期加入相同的起訖時間。
2. 同一天可重複加入多段互不重疊時段；重疊、結束早於開始與未選星期必須拒絕。
3. 管理者可逐筆刪除每週時段與日期例外；`closed` 休診優先於 `extra_open` 加開。
4. 固定不開放時間可自訂；初診限整點／30 分，回診限 15 分／45 分，格式不符須拒絕。
5. 櫃台處理清單依看診時間排序（越近的越前面），預設只看待處理預約；可搜尋姓名、電話或預約編號，並可依狀態、掛號別與患者篩選。
6. 高頻「到診」與目前狀態最重要的合法動作直接顯示為主按鈕；改期、取消、未到等次要動作收進「更多處置」。不合法或無權限的動作不得渲染成看得到卻不能用的按鈕。
7. 回診只能呈現醫師的明確決定；系統與 AI 不得自行做臨床判斷。主管或櫃台只負責登錄，畫面與資料需分別留下「回診決定者：醫師」及資料登錄者。回診項目可複選，並可記錄診斷書份數。目標為「日期＋時間」，僅限營業日的回診可掛號網格；未營業日期會即時提示且無法儲存。確認「需要回診」後會產生一筆回診提醒的日曆投影（上日曆），並在櫃台處理清單顯示「待安排回診」，供櫃台安排下次門診時段；改為「目前無需回診」則移除該投影。
8. 個管工作量只顯示個管 ID、月份、不重複患者數與規則版本，不計算或顯示薪資。
9. 帳號管理只建立標籤與角色；至少保留一個啟用中的管理者。
10. 患者公告只在 `published` 時顯示；維護模式啟用後，患者預約流程必須完全隱藏並移出互動／無障礙樹，直接呼叫合成 store 也必須拒絕建立預約。關閉或到達恢復時間後才可重新顯示流程。
11. 發布紀錄只代表目前瀏覽器中的操作紀錄，不會觸發 Firebase 或正式環境部署。
12. 清除本機資料只屬主管的「進階設定／危險區域」；櫃台的 DOM、hash 深連結與直接 store 呼叫都不可觸及。清除成功必須留下 `local_state_reset` 稽核事件並登出。

## 患者端流程

患者頁使用四個可返回修改的步驟：

1. 選擇「初診」或「回診」，再選看診項目（止鼾／醫美）。回診尚未經醫師確認時不可進入選時段。
2. 時段依日期分組，以 `Asia/Taipei` 顯示**單一時間點**（24 小時制）。掛號本來就只需要起始時間，不顯示區間。
3. 填寫姓名、電話、生日、身分證與健保卡，並勾選資料保存告知後才可送出。
4. 顯示預約編號與狀態，並提供 `.ics` 下載與 Google 日曆連結。若取消同一筆預約，完成卡與下方預約卡必須同步改為「取消待診所確認」。

行事曆匯出的內容只包含診所名稱、掛號別、時間與地址，**不含身分證、看診項目或備註**——許多人的行事曆與家人共用，因此適用與日曆投影相同的最小化原則。

患者端與診所端的事件刻意不同（2026-07-22 專案負責人指定）：

| | 患者自己的行事曆 | 診所端日曆投影 |
| --- | --- | --- |
| 時間 | **只標記開始時間**（`DTSTART` 無 `DTEND`，RFC 5545 §3.6.1） | 開始到結束**一小時**（`CLINIC_EVENT_MINUTES`） |
| 顏色 | `COLOR:green`（RFC 7986，**盡力而為**：Google 匯入會忽略） | Google API `colorId`，綠色 |
| 提醒 | 前一天同一時刻（`TRIGGER:-P1D`） | 由診所日曆自身設定 |

患者端不佔區間的理由：行事曆常與家人共用，一個時間點就夠了；佔掉一段時間反而讓對方誤以為那段時間都不能安排。顏色只當加分，不得用來承載必要資訊。

頁首提供主導覽、環境徽章與患者公告；正式線上患者頁不得顯示內部工作臺入口。頁尾說明資料保存範圍。桌面、平板與 320px 手機寬度不得產生整頁水平溢出，互動控制需保留清楚的鍵盤焦點樣式。

## UI/UX 基線（2026-07-21 依外部準則檢核後訂定）

依據時段選擇器與無障礙表單的公開設計準則，以下為兩端共用、且不得回退的規則：

| 規則 | 為什麼 | 落點 |
| --- | --- | --- |
| 時段依日期分組，日期只在群組標題出現一次 | 平鋪清單會讓每格重複日期，無法快速掃視「這天有哪些時間」 | `ui-format.js` 的 `groupSlotsByDate` |
| 時段只顯示單一時間點，24 小時制 | 避免 AM/PM 誤讀；掛號本來就只需要起始時間 | `admin-view.js`、`patient-app.js` |
| 明確標示時區為 Asia/Taipei（台北時間） | 沒有時區脈絡的時間在跨裝置情境會出錯 | 兩端的時段說明文字 |
| 選取狀態不單靠顏色 | 色覺障礙者無法辨識 | 邊框粗細 + 勾號 + `aria-pressed` |
| 觸控目標至少 44px | 行動裝置誤觸 | `.slot-chip`、`.text-button` |
| **送出按鈕不得因驗證未過而停用** | 停用的按鈕不會說明「為什麼不能按」，使用者只能猜 | 按下後逐欄提示並聚焦第一個問題欄位 |
| 錯誤在離開欄位後才提示，送出時全部攤開 | 邊打邊報錯很煩躁；送出時則要一次講完 | `patient-app.js` 的 `touched` 集合 |
| 錯誤訊息以 `aria-describedby` 綁定欄位，並帶 `role="alert"` 與 `aria-invalid` | 螢幕報讀者需要知道是哪一欄、錯在哪 | `patient.html` |
| 必填以文字說明加符號標示，不只用顏色 | 同上 | `.required-mark` 與表單說明 |
| 錯誤訊息要說「怎麼填才對」而非只說「格式錯誤」 | 可行動的訊息才有用 | `patient-registry.js` 的 `fieldErrors` |
| **回饋出現在操作點**：每個表單旁有就地 `form-status`，成功與失敗原因顯示在剛按下的按鈕旁；全域狀態列透過 `aria-live` 播報。桌面可 sticky，手機改為一般文流，避免遮住焦點與內容 | 長頁面上只寫頁首等於沒有回饋；但窄螢幕同時固定導覽與狀態列會吃掉大量可視高度 | `message(text, tone, anchorId)`（兩端）、`.status-banner`／`.status-message` |
| 預約失敗必須寫出原因（「未建立預約：…」），成功寫出編號與時間 | 使用者要能不捲動就確認結果與補救方向 | `admin-bootstrap.js`、`patient-app.js` 的 booking handlers |
| 每個必勾項目未勾時要有文字錯誤，不得只移動焦點 | 沒有文字的拒絕看起來像沒反應（WCAG 3.3.1） | `synthetic-confirmation-error` |
| 步驟切換把焦點移到新步驟標題，指示器帶 `aria-current="step"` | 鍵盤與報讀使用者不會停留在原地迷失 | `patient-app.js` 的 `showStep` |
| 患者資料步驟包在 `<form novalidate>` 內，Enter 可送出並走同一套驗證 | 鍵盤慣例；novalidate 保留「一次攤開全部錯誤」模式 | `patient.html` 的 `patient-booking-form` |
| 到診等高頻／當下主要動作直接顯示；次要選單只保留目前可執行的動作，與 `actionEnabled` 同一閘門 | 每次到診都先開選單增加操作成本；看得到但必被拒絕的按鈕也只會製造困惑 | `admin-view.js` 的 `primaryAction`、`actionMenu` |
| 櫃台可依醫師指示登錄回診決定並做個管首次指派；個管改派只限主管，櫃台只顯示唯讀結果 | 臨床決定、資料登錄與人員改派是不同責任，不可混成同一權限 | `permissions.js`、`admin-view.js`、`store.js` |
| 桌面先顯示週排程，手機預設收合週排程與工作臺設定；建立預約採漸進揭露，成功後自動收合並回到新預約卡 | 長日曆、帳號設定與數十個時段不應擋住每日高頻清單；完成任務後應回到下一個工作點 | `syncResponsiveDisclosures`、`#booking-workflow` |
| 建立類表單成功後清空輸入；同名帳號在狀態轉換層拒絕 | 防止殘留值連按兩次建立重複資料 | `workspace-domain.js` 的 `createAccount` |
| sticky 導覽列與狀態列必須不透明 | 半透明會與底下內容疊字（2026-07-22 截圖實證） | `.workspace-nav`、`.status-banner` 用 `--surface` |
| 確認一律走自製 `<dialog>` 彈窗，禁止 `window.confirm` | 原生 confirm 無法設樣式與主題；`showModal` 內建焦點陷阱與 Esc，取消鈕優先聚焦 | `modules/confirm-dialog.js`；`check:ui` 強制 |
| 色彩一律用 design token，不得硬編碼 | 主題系統靠 token 覆蓋；硬編碼會在護眼／深色主題漏網 | `styles.css` 的 `:root` 與 `[data-theme]` 區塊 |
| 主題四段：自動／淺色／護眼／深色；深色對比 ≥ WCAG AA | 尊重系統偏好與護眼需求；實測全配對 ≥ 6.19:1 | `theme.js`（head 同步載入防閃爍）＋ `#theme-picker` |
| 患者端第 2 步顯示目前選擇並可返回；第 3 步可直達第 1 步重選 | 選錯類型的人要能發現並輕鬆重來（NN/g #3） | `#booking-context` 與雙返回鈕 |
| 二元選擇按鈕（類型／項目）帶 `aria-pressed` | 選取狀態不能只靠顏色 | `renderBookingTypeButtons`、`renderServices` |
| 預約以**週檢視**呈現：左時間軸＋週一～週日七欄；單一事件使用完整日欄，只有時間實際重疊時才分成穩定並行欄，休診日斜線，可週導覽，點事件捲到清單卡片 | 固定半欄會讓內容無故截斷；按實際重疊分欄才同時保留可讀性與衝突辨識 | `modules/week-view.js` |
| 週檢視的定位一律用 `data-top`／`data-height` ＋ CSSOM 套用，**不得用 inline `style` 屬性** | CSP 是 `style-src 'self'`（無 `'unsafe-inline'`），會擋掉 style 屬性——屬性在、但完全不生效（實機驗證） | `hydrateWeekView` |
| 日曆投影死信提供操作者「重新排入」入口（合成示範），只作用於死信 | runbook 步驟 3 的人工補回需要一個可操作的入口；權威邏輯在 `apps/worker` | `renderOutbox`＋`requeueOutboxJob` |
| 手機（≤48rem）篩選列用 2 欄格線，搜尋與狀態並排，結果數與清除按鈕保持可見 | 多個全寬欄位會佔滿整個畫面；常用搜尋也不能藏到額外面板 | `workbench.css` 的 `.filter-bar` 媒體查詢 |
| 多欄容器（帳號治理、月度統計、事件、排班比較）在 ≤30rem 收成單欄 | 44rem 斷點的 2 欄到手機只剩約 156px，表單欄位與統計數字塞不下就溢出容器（2026-07-22 實機回報）。週次選擇例外，短標籤放得下 | `styles.css` 的 30rem 媒體查詢 |
| 浮動選單不得超出視窗：手機版處置選單往右開 | 靠左的按鈕沿用 `right:0` 會往左展開出螢幕 | `.action-menu-list` 媒體查詢 |
| 回診目標必須是「日期＋時間」，且僅限營業日的回診網格（:15/:45、扣除固定不開放與休診例外）；未營業日期不可選 | 只有日期無法排程；未營業日的目標無法兌現。日期與時間類輸入一律同理 | `followUpDueTimes`（與時段產生共用語意）＋ `recordFollowUp` 驗證 |
| 工作臺一次只顯示一個工作區，導覽以 hash 深連結切換，帶 `aria-current="page"` 並把焦點移到該區標題 | 七個工作區疊在一頁需要大量捲動；hash 保留深連結、上一頁與無 JS 可用性（決策理由見架構文件） | `modules/workspace-tabs.js` |
| 分頁可見性與權限的判斷集中在一處（`data-restricted` 由 bootstrap 標記，`hidden` 由分頁模組決定） | 兩邊各自寫 `hidden` 會互相蓋掉，櫃台切到管理者分頁會看到空白頁 | 同上 |
| 備註可在預約卡就地修改，且不改狀態、不動時段、不產生日曆投影，但寫稽核 | 備註是營運註記而非臨床決定；已取消／未到的預約不再修改 | `updateAppointmentNotes` |
| 回診卡的個管指派是捷徑，與「個案管理」分頁共用同一個 domain 函式與稽核事件，且**各自檢查權限** | 在別的表單裡順手做，不代表可以繞過該動作的授權 | `store.js` 的 `/follow-ups/:id` 路由 |
| 櫃台的主管專屬導覽與區塊必須從 DOM 移除；受限 hash 回首頁；直接 action／store 仍各自拒絕 | 隱藏不是授權。結構、路由、動作與資料層需同時守住界線 | `enforceRoleDomBoundary`、`workspace-tabs.js`、`post`、`store.js` |
| 通知鈴鐺顯示未讀數量，清單是非 modal popover；`Esc`／點外關閉並把焦點還給鈴鐺，開關不得改變 header 高度 | 通知是輔助入口，不能打斷目前工作或造成版面位移 | `admin-bootstrap.js`、`#notification-popover` |
| 手機 header 的品牌、通知與設定同列；320px 加 200% 文字縮放仍不得整頁水平溢出 | 行動櫃台需要保留主要入口，文字放大也必須重排 | `workbench.css` 極窄斷點與 Playwright 回歸 |

驗證方式：`corepack pnpm check:ui` 檢查結構與安全界線；版面與焦點行為需以
瀏覽器在桌面、375px 與 320px 寬度各確認一次，且不得出現整頁水平溢出。

## 安全與可維護性規則

- 患者資料欄位採允許清單（見上方「資料範圍」），身分證一律遮罩顯示。
- 自訂公告、維護說明、帳號標籤與發布摘要不得輸入患者、員工或憑證資料。
- 所有動態內容都必須經過 `escapeHtml`。這一點以實際 payload 驗證過，不只靠閱讀程式碼：`<img onerror>`、`<svg onload>` 與 `<script>` 注入姓名、備註與公告後，注入節點數為 0。
- 不載入外部字型、追蹤碼、遠端圖片或第三方 UI 資產；`check:ui` 會掃描客戶端程式碼中的任何 http(s) 端點。
- `index.html`（工作臺）／`patient.html`（患者端）負責語意結構，`styles.css` 與 `workbench.css` 集中設計 token 與元件樣式，`admin-bootstrap.js`／`patient-app.js` 只處理互動與渲染，`store.js` 與 `modules/` 集中狀態轉換。
- 正式 API、行動 App 與 NAS 必須共用 domain API；不得讓任何客戶端直接寫 Firestore。
